# Verification: cross-cutting

How to run this file: bring up the local production build with the fixtures as described in [the verification README](README.md#how-to-run-a-pass), and run every P1 item in the five tables before any P2 or P3 item. Start each table from freshly loaded fixtures, and reload them (`npx dotenv -e {env file} -- node product-description/verification/scripts/fixtures.cjs`, then close every browser context so no prefetched page survives) after any item that posts a comment, likes, saves a field, archives, adds a solution or problem, starts an attempt, accepts an invite, chooses a testsolver type or runs SQL; items that only look (math previews, Tab orders, layout at a width) can run back to back. SQL in a Setup cell runs against the same throwaway database in an interactive `psql "$DATABASE_URL"` session (which avoids shell quoting around `$` and `'`); settings are read when a page is built, so load the page after running it. Setup **Preview** means the add-problem form used as a scratch pad: Wes Writer on `/c/demo/add-problem` (he already has an author in `demo`, so the page creates nothing), click the empty "PROBLEM STATEMENT" box, type the text given in Steps (Enter starts a new line there), click the empty page margin left of the form to close the box, read the result, and reload the page before the next string; never press "Submit" in a Preview item. When an item does submit the add-problem form, click the page margin first so no box above "Submit" is open, and click again if the first click is lost (B-18). Two production-build side effects matter here: an Admin or TeamMember who views a collection page gets an author there (B-14), which makes "Add Solution" appear for them, and cards, chips and back links are prefetched a moment after they appear, so keep to each item's stated waits. The Device column: a role (`admin` Ada Admin, `writer` Wes Writer, `member` Tia Member, `serious` Sam Serious, `serious2` Sue Serious, `casual` Cal Casual, `unchosen` Uma Unchosen, `viewer` Vic Viewer, `stranger` Stan Stranger, `student` Eve Student, `signed out`) is who the browser is signed in as, and two roles mean two browser contexts (two browsers, or a normal and a private window), never two tabs; `second tab` is the same user in another tab of the same context; `prod build` marks items that hold only on `next build` + `next start`; `dev server` means the item needs `next dev` on the same database instead; `slow server` delays server actions by 2–3 seconds (a Playwright route handler, or devtools throttling, which slows everything); `offline` is devtools' Offline set after the page has loaded; `db` means the Setup runs SQL; `narrow` is a window 375 pixels wide (devtools' device toolbar is enough; other widths are given in the Steps); `phone` is a real phone reaching the instance over the local network, with the session cookie set through remote debugging (Safari Web Inspector or `chrome://inspect`); `keyboard` is keyboard only, no pointer; `screen reader` is VoiceOver or NVDA, or the browser's accessibility tree where the Expected names a role or a name; `hand` needs a person to judge something visual or timed.
