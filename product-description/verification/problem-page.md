# Verification: problem page

How to run this file: bring up a local production build with the fixtures loaded, as in [How to run a pass](README.md#how-to-run-a-pass). Every row starts from freshly loaded fixtures unless its Setup says otherwise, and any row that likes, comments, adds or edits a solution, saves a field, archives, starts an attempt, submits a problem, accepts an invite or runs a database step changes the state later rows expect, so reload the fixtures after it (at the latest before the next row that touches the same problem or user). In the fixtures no problem has a like or a comment, so every heart starts gray at "0" and every discussion is empty; `demo` `A1` and `N1` have one solution each by "Default Author" (an author with no user), while `demo` `C1`, `G1`, `A2`, `A3` and the fillers have none; the `demo` collection page lists newest first, so `A24` to `A5` fill page 1 and `A4`, `A3`, `G1`, `C1`, `N1`, `A1` are on page 2. Wes Writer has an author in `demo` and `ts`, Ada Admin only in `aime`, and no one else has one. On a production build, merely viewing a collection page gives an Admin or TeamMember an author there (the "Add Problem" link is prefetched), which makes "Add Solution" appear, so in every row whose Setup says a user has no author, open the problem page by typing its address and do not visit the collection page first. The Device column names the fixture user the browser is signed in as: `admin` Ada Admin, `writer` Wes Writer, `member` Tia Member, `serious` Sam Serious, `serious2` Sue Serious, `casual` Cal Casual, `unchosen` Uma Unchosen, `viewer` Vic Viewer, `submitter` Sid Submitter, `stranger` Stan Stranger, `signed out` no session cookie; two roles mean two browser contexts side by side. The other values are the README's [devices and conditions](README.md#devices-and-conditions): `second tab` (the same user in a second tab of the same context), `prod build`, `slow server` (actions delayed 2 to 3 s), `offline` (set after the page has loaded), `narrow` (375 px wide), `keyboard`, `screen reader` and `hand` (a person must watch). "Action requests" are the POST requests carrying a `next-action` header in devtools' Network panel; rows that count requests filter on that header. "Delete the session cookie" means removing `authjs.session-token` for `localhost` in devtools, which ends the session. "Forced failure" means a Playwright route handler that delays every `next-action` request by 2 s and aborts the first one only. Database steps run SQL against the verification database, never production, with these shorthands: `‹demo›` is `(SELECT id FROM "Collection" WHERE cid = 'demo')`; `‹Wes›` is `(SELECT id FROM "User" WHERE name = 'Wes Writer')`, and likewise `‹Ada›`, `‹Vic›`, `‹Sam›` and so on by first name; `‹demo C1›` is `(SELECT id FROM "Problem" WHERE pid = 'C1' AND "collectionId" = ‹demo›)`. "Demote Wes in `demo` to ViewOnly" means `UPDATE "Permission" SET "accessLevel" = 'ViewOnly' WHERE "userId" = ‹Wes› AND "collectionId" = ‹demo›`, other roles alike; "remove Vic's permission in `demo`" means `DELETE FROM "Permission" WHERE "userId" = ‹Vic› AND "collectionId" = ‹demo›`; "delete `demo` `C1`" means `DELETE FROM "Problem" WHERE id = ‹demo C1›`; "move Sam's `ts` `N1` start back {m} minutes" means `UPDATE "SolveAttempt" SET "startedAt" = (now() AT TIME ZONE 'UTC') - interval '{m} minutes' WHERE "userId" = ‹Sam› AND "problemId" = ‹ts N1›`. `ts` `N1` has difficulty 2, so a 15-minute time limit; `ts` `A1`, `C1`, `A2` and `N2` have difficulty 1 (10 minutes). Rows that press "Give Up" do so with the answer box empty; the browser may then show "Please fill out this field" on the box while the give-up goes through, which is B-05 in the [bug triage](../bug-triage.md) and not what those rows check. A claim ending in a triage ID such as "(B-19)" describes a behavior filed under that entry. A Result of `pass (scripted: {check})` records that a check of the first scripted pass ([results so far](README.md#results-so-far)) demonstrated the row; it covers only what that check looked at, so run the row by hand as well before marking a document verified.
