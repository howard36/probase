# Verification: foundations and entry

How to run this file: run it on the production build and fixtures described in the [README](README.md#how-to-run-a-pass), signed in by minted session cookie as the fixture user the Device column names (`admin` Ada Admin, `writer` Wes Writer, `member` Tia Member, `serious` Sam Serious, `serious2` Sue Serious, `casual` Cal Casual, `unchosen` Uma Unchosen, `viewer` Vic Viewer, `submitter` Sid Submitter, `stranger` Stan Stranger, `student` Eve Student, or `signed out` with no cookie); two roles joined by `+` mean two separate browser contexts (two browsers, or a normal and a private window), never two tabs. A Setup that begins "Fresh fixtures" needs the fixtures reloaded first, because earlier items accept invites, like, comment, edit `demo` `C1`, start attempts or change the database; reloading needs no server restart and minted cookies stay valid, and after any item with a `DB` change reload before the next item that depends on the same records. On the production build merely viewing `/c/demo` gives Ada, Wes and Tia (any Admin or TeamMember) an author there ([B-14](../bug-triage.md#b-14-viewing-the-collection-page-creates-an-author)), so items that need a member without an author say "do not open `/c/demo` first". "Delete the session cookie" means removing `authjs.session-token` in devtools (Application, Cookies); "restore" means setting a freshly minted one. SQL in Setup or Steps runs in `psql "$DATABASE_URL"` against the verification database; create two helpers once, which survive fixture reloads because those only empty tables: `create function c(text) returns int language sql as 'select id from "Collection" where cid = $1';` and `create function p(text, text) returns int language sql as 'select p.id from "Problem" p join "Collection" c on c.id = p."collectionId" where c.cid = $1 and p.pid = $2';`. The fixture instance has `topsoj` and `otis-mock-aime` but no `cmimc`, so, unlike the bare "local instance" the documents mention, only the sidebar's CMIMC link leads to "Page not found". The other Device values: `prod build` (holds only on the production build), `dev server` (`npx dotenv -e {env file} -- next dev -p 3001` against the same database and secret, opened at `http://localhost:3001`; the same cookie works because cookies are not scoped by port), `slow server` (server actions delayed 2 to 3 seconds: the Playwright route handler from the README, or by hand a devtools throttling profile with 2500 ms latency, which also slows navigations), `slow network` (a devtools throttling profile with 3000 ms latency, for items about a link that is still loading), `offline` (devtools Network set to Offline after the page has loaded), `second tab`, `narrow` (a window 375 px wide), `keyboard`, `screen reader`, `hand` (a person must judge something visual or a timing), `DB` (the item changes the database), `Firefox` and `Safari` (run in that browser instead of Chromium), and `Google`, which needs a real Google sign-in: an OAuth client whose redirect URI is `http://localhost:3000/api/auth/callback/google`, set as `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, and real Google accounts, "A" and, where the Setup says so, a second account "B" (the fixture users' `example.com` and `example.edu` addresses cannot sign in through Google); without a real client a `Google` item is blocked, not failed, while items that only need the browser to leave for Google work with the placeholder client.

- Whether the interface should let people change a problem's subject or difficulty, remove an answer, or delete anything is a product call ([Open questions and verification](../foundations/data-model.md#open-questions-and-verification), B-32); DATA-02, DATA-10 and DATA-24 check the current behavior.

Not checkable by hand:

- "Page not found" says the problem or collection "was removed" although nothing can be removed through the interface, and "You need permission" advises switching accounts with no way to sign out; both are copy and product questions ([Edge cases](../entry/error-pages.md#edge-cases), [Open questions and verification](../entry/error-pages.md#open-questions-and-verification), B-31).
- A failure that happens while drawing in the browser and then passes, the one case "Try again" recovers from, cannot be produced by hand in Probase, whose pages are built on the server ([Submit](../entry/error-pages.md#submit)).
- A failure at the moment a countdown reaches zero needs the problem to break in the last second of an attempt; ERR-38 checks the same refresh path after an action ([Open questions and verification](../entry/error-pages.md#open-questions-and-verification)).
