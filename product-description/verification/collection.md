# Verification: collection

How to run this file: run every item on the production build and throwaway database described in [How to run a pass](README.md#how-to-run-a-pass), in a desktop window 1440 × 900 unless the Device or Setup says otherwise, with the [fixtures](README.md#fixtures) loaded. The items use `demo` "Probase Demo" (ShortAnswer, authors hidden; 26 problems not archived, so two pages: `A24` down to `A5`, then `A4`, `A3`, `G1`, `C1`, `N1`, `A1`; `A2` is archived), `ts` "Testsolve Lab" (Integer, requires testsolving; six problems, all by Wes Writer; "the test page" means `/c/ts/t/mock-contest-1-1`, test 1, "Mock Contest #1", holding `A1`, `N1` and `A2` at positions 1 to 3), `aime` "AIME Lab" (AIME, difficulty and solution optional), `otis-mock-aime` (no problems, its own difficulty labels) and `topsoj` (no members; joined through the `join-topsoj` invite, which makes the member Serious). Reload the fixtures before any item whose Setup says "fresh fixtures", and after every item that submits the add-problem form, saves an edit, likes, comments, starts an attempt, archives, accepts an invite, chooses a testsolver type or edits the database; the next item assumes fixture state unless its Setup says "right after" another item. Viewing changes state too: on a production build an Admin or TeamMember who opens a collection page gets an author there, so run the items that need Tia Member without an author straight after a reload, before anyone signs in as her. "Add {n} extra problems to `{cid}`" means running `psql "$DATABASE_URL" -c "INSERT INTO \"Problem\" (\"collectionId\", pid, title, statement, subject, \"isAnonymous\", difficulty, answer, \"createdAt\") SELECT c.id, 'N' || (100 + g), 'Extra problem ' || g, 'Extra statement ' || g || '.', 'NumberTheory'::\"Subject\", false, 1, '1', c.\"createdAt\" + interval '1 hour' + g * interval '1 second' FROM \"Collection\" c, generate_series(1, {n}) g WHERE c.cid = '{cid}'"` with `DATABASE_URL` from the env file: it adds Number Theory problems `N101` onward (difficulty 1, answer 1, no author) created an hour after the collection, so they list after every fixture problem, newest (`N{100+n}`) first, and in `ts` they are locked for Serious testsolvers. Other database edits are given by table and column; fixture user ids are `u-` and the role key (`u-viewer`, `u-writer`). "Delete the session cookie" means removing `authjs.session-token` for `localhost` in devtools (Application, Cookies); "stop the database" means stopping the Postgres server after the page has loaded, and starting it again after the item; "view the source" means the source of a full page load (Ctrl+U), which holds everything the server sent. In the Device column a role key names the fixture user the browser is signed in as (`admin` Ada Admin, `writer` Wes Writer, `member` Tia Member, `serious` Sam Serious, `serious2` Sue Serious, `casual` Cal Casual, `unchosen` Uma Unchosen, `viewer` Vic Viewer, `submitter` Sid Submitter, `stranger` Stan Stranger, `signed out`), and `+` joins a second role in a second browser context; `second tab`, `prod build`, `slow server`, `offline`, `narrow`, `keyboard`, `screen reader` and `hand` are as in [Devices and conditions](README.md#devices-and-conditions). Two values are added here: `slow page` delays page fetches rather than actions, which is what search, filter and page changes wait on (in Playwright, hold every request carrying an `rsc` header for 2 to 3 seconds; by hand, devtools throttling at "Slow 3G"), and `dev server` runs the item on `next dev` instead of the production build. "Record what happens" marks a suspected bug: write down what the app did, then compare it with what the document says, which follows. Rows marked `pass (scripted: …)` were shown by the scripted first pass ([Results so far](README.md#results-so-far)); they still need a run by hand before a document is marked verified.
